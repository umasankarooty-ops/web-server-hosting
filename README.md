# Web Server Hosting
## 1. Project Overview

This project demonstrates web server installation, configuration, hosting, and security testing using an AWS EC2 Linux instance.

The lab covers Apache HTTP Server configuration, PHP application hosting, virtual hosts, database integration, URL rewriting, custom error pages, and basic web server security testing.

The project also documents the process of maintaining configuration files and application code in GitHub for version control and submission.

## 2. Objectives

- Install and configure Apache on a Linux server.
- Install PHP and database services.
- Host PHP and HTML applications on an EC2 instance.
- Configure multiple Apache virtual hosts.
- Explore Apache configuration files.
- Configure `.htaccess` and URL rewriting.
- Disable directory listing.
- Configure custom HTTP error pages.
- Test common web server security misconfigurations.
- Document results and manage source code using Git and GitHub.
- Understand the difference between local virtual machine hosting, cloud hosting, and free PHP hosting.

## 4. Architecture

The project follows a simple web application architecture.

1. A client browser sends an HTTP request.
2. AWS EC2 receives the request through its public IP address and security group.
3. Apache receives the request and selects the appropriate website.
4. PHP processes PHP application files when requested.
5. The application can communicate with the local database.
6. Apache returns the HTTP response to the client.

### Architecture flow

```text
Client Browser
      |
      | HTTP :80
      v
AWS EC2 Security Group
      |
      v
Apache HTTP Server
      |
      +---- Virtual Host: site1.local
      |           |
      |           +---- HTML / PHP files
      |           +---- .htaccess rules
      |
      +---- Virtual Host: site2.local
      |           |
      |           +---- HTML files
      |
      +---- PHP Application
                  |
                  v
             MariaDB Database
```

Note: `site1.local` and `site2.local` are lab hostnames. They are not public domain names. Local host-header tests can be performed using `curl`.

## 7. Apache Virtual Host Configuration

Virtual hosts allow Apache to serve different websites from one server.

### 7.1 Create website directories

```bash
sudo mkdir -p /var/www/site1
sudo mkdir -p /var/www/site2
```

Create test pages:

```bash
echo '<h1>Website One</h1>' | \
sudo tee /var/www/site1/index.html

echo '<h1>Website Two</h1>' | \
sudo tee /var/www/site2/index.html
```

Set directory ownership:

```bash
sudo chown -R apache:apache /var/www/site1 /var/www/site2
```

### 7.2 Create the virtual host configuration

Configuration file:

```text
/etc/httpd/conf.d/sites.conf
```

Example configuration:

```apache
<VirtualHost *:80>
    ServerName site1.local
    DocumentRoot /var/www/site1

    <Directory /var/www/site1>
        Require all granted
        AllowOverride All
    </Directory>
</VirtualHost>

<VirtualHost *:80>
    ServerName site2.local
    DocumentRoot /var/www/site2

    <Directory /var/www/site2>
        Require all granted
        AllowOverride All
    </Directory>
</VirtualHost>
```

### 7.3 Validate and reload Apache

```bash
sudo apachectl configtest
sudo systemctl reload httpd
```

Expected configuration validation result:

```text
Syntax OK
```

### 7.4 Test virtual host selection

```bash
curl -H "Host: site1.local" http://localhost/
curl -H "Host: site2.local" http://localhost/
```

Expected results:

- The first request returns `Website One`.
- The second request returns `Website Two`.

These tests verify that Apache selects the correct virtual host based on the HTTP Host header.

## 9. Directory Listing and URL Rewriting

### 9.1 Purpose

Directory listing can expose filenames when a directory does not contain a configured index document.

URL rewriting allows Apache to map a requested URL to another resource or enforce access restrictions.

### 9.2 Configure `.htaccess`

Example file:

```text
/var/www/site1/.htaccess
```

Example configuration:

```apache
Options -Indexes
RewriteEngine On

ErrorDocument 403 /403.html
ErrorDocument 404 /404.html
ErrorDocument 500 /500.html

RewriteRule ^home$ index.html [L]
RewriteRule ^private(/.*)?$ - [F,L]
```

The directives perform the following functions:

- `Options -Indexes`: disables automatic directory listing.
- `RewriteEngine On`: enables URL rewriting.
- `ErrorDocument`: defines custom error-page locations.
- `RewriteRule ^home$ index.html [L]`: internally maps `/home` to `index.html`.
- `RewriteRule ^private(/.*)?$ - [F,L]`: returns HTTP 403 for requests matching the private path.

The `AllowOverride All` setting in the virtual host permits `.htaccess` directives to be processed.

### 9.3 Validate and reload

```bash
sudo apachectl configtest
sudo systemctl reload httpd
```

### 9.4 Test URL rewriting

```bash
curl -i -H "Host: site1.local" http://localhost/home
```

Expected result: HTTP 200 if `index.html` exists and the rule is active.

### 9.5 Test private path restriction

```bash
curl -i -H "Host: site1.local" http://localhost/private/
```

Expected result:

```text
HTTP/1.1 403 Forbidden
```

This verifies the access restriction when the rewrite rule is present and working.

## 10. Custom HTTP Error Pages

The project uses custom pages for common HTTP errors.

Create the pages:

```bash
for code in 403 404 500; do
    echo "<h1>Error $code</h1>" | \
    sudo tee "/var/www/site1/$code.html"
done
```

Configured error pages:

| HTTP status | Meaning |
|---|---|
| 403 | Forbidden |
| 404 | Resource not found |
| 500 | Internal server error |

The `.htaccess` directives map these status codes to the corresponding HTML pages.

Example test for a missing page:

```bash
curl -i -H "Host: site1.local" \
http://localhost/missing-page
```

Expected result: HTTP 404 with the configured error-page content.

A custom 500 page is configured, but its appearance does not prove that the server has correctly recovered from an application error. The server should not be deliberately crashed for this test.

## 12. Security Misconfiguration Testing

Security tests must be performed only against systems and files that the lab operator is authorized to test.

### 12.1 Test for exposed PHP information

Create a temporary diagnostic file:

```bash
echo '<?php phpinfo();' | \
sudo tee /var/www/site1/phpinfo.php
```

Test it locally:

```bash
curl -I -H "Host: site1.local" \
http://localhost/phpinfo.php
```

If a full response is required for the controlled test, inspect it locally and do not publish the diagnostic output.

Remove the file immediately after testing:

```bash
sudo rm -f /var/www/site1/phpinfo.php
```

Expected security outcome: No public diagnostic PHP information page remains deployed.

### 12.2 Test for exposed backup files

Create a harmless test file:

```bash
echo 'Temporary backup test' | \
sudo tee /var/www/site1/test.bak
```

Request the test file:

```bash
curl -i -H "Host: site1.local" \
http://localhost/test.bak
```

Record whether the file can be retrieved. Remove it after testing:

```bash
sudo rm -f /var/www/site1/test.bak
```

Security recommendation: Store real backups outside the public document root and restrict access to sensitive files.

### 12.3 Test directory traversal protection

Run a controlled request against the lab server:

```bash
curl --path-as-is -i \
-H "Host: site1.local" \
'http://localhost/site1/%2e%2e/%2e%2e/etc/passwd'
```

Expected security outcome: Operating-system files must not be disclosed through the web application.

Interpret the response carefully. An HTTP error by itself is not proof that all directory traversal vulnerabilities are prevented. Review the response body, Apache configuration and application behavior.

### 12.4 Test file upload restrictions

For an application with an upload form, evaluate:

- Whether permitted file types are explicitly defined.
- Whether file extensions and actual content are validated server-side.
- Whether maximum file size is enforced.
- Whether uploaded files are stored outside executable web directories where practical.
- Whether uploaded content can be executed by the server.
- Whether filenames are sanitized and permissions are restrictive.

Do not upload executable or malicious files to a public server. If the application has no upload functionality, document this test as not implemented rather than claiming it passed.

### 12.5 Review logs

```bash
sudo tail -n 50 /var/log/httpd/access_log
sudo tail -n 50 /var/log/httpd/error_log
```

Logs help identify requests, response codes and configuration problems.

## 17. Troubleshooting

### Apache configuration error

```bash
sudo apachectl configtest
```

Review the output and correct any reported configuration errors before reloading Apache.

### Apache service not running

```bash
sudo systemctl status httpd
sudo journalctl -u httpd --no-pager -n 50
```

### URL rewrite rule not working

Check that the rewrite module is loaded:

```bash
sudo httpd -M | grep rewrite
```

Check that `AllowOverride All` is configured for the correct document root and that `.htaccess` contains `RewriteEngine On`.

### HTTP 403 instead of HTTP 200

Check the access restrictions, document-root permissions, `.htaccess` directives and Apache error log.

### Website inaccessible from the internet

Check the EC2 public IPv4 address, security-group inbound rules, Apache service status and local firewall configuration.

### Git push rejected

Verify the remote URL, authentication method, branch name and repository permissions.

## 18. Security Best Practices

- Restrict SSH access to trusted IP addresses.
- Allow only required inbound ports.
- Disable directory listing where it is not needed.
- Do not expose PHP diagnostic pages.
- Keep sensitive files outside public document roots.
- Use least-privilege database accounts.
- Keep the operating system and server packages updated.
- Use HTTPS for real public websites.
- Review access and error logs regularly.
- Store secrets outside source control.
- Keep vulnerable applications such as DVWA isolated.
- Remove temporary security-testing files after testing.
- Stop or delete cloud resources that are no longer required, after preserving the project files.
